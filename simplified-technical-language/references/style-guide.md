# Simplified Technical Language 规范

版本：1.0  
依据：ASD-STE100 Issue 9（2025 年 1 月）的公开说明与可迁移写作原则。

本规范面向日常中文技术写作，必要时保留或生成英文。它提炼标准的方法，不照搬标准全文。中文规则和个人阈值均为本地适配，不代表 ASD 官方解释。

## 1. 适用范围

### 1.1 默认适用

- 操作步骤、配置说明、故障排查和安全提示。
- 技术笔记、README、设计说明、决策记录和实验记录。
- Issue、PR 描述、错误消息、工具描述和 Agent 指令。
- 技术报告、学习总结和需要清楚传递事实的日常说明。

### 1.2 选择适用

- 论文、论证和复杂概念解释：保留完整推理、引用和领域惯用结构，不为短句破坏逻辑。
- 聊天记录、访谈和原始实验日志：改写副本，不覆盖原始记录。
- 代码注释和提交信息：服从项目约定；没有约定时再应用本规范。

### 1.3 不强制适用

- 文学、营销、品牌、说服性文案和需要修辞的文本。
- 必须原样保留的引文、标准条文、合同、代码、命令和界面文本。
- 已有强制风格指南的项目。项目规则优先，冲突时列出差异。

语言规范只能改善表达，不能证明技术内容真实或安全。

## 2. 核心写作原则

| 编号 | 规则 | 可执行判据 |
|---|---|---|
| G1 | 事实优先 | 保留条件、例外、范围、否定、数字、单位和来源。 |
| G2 | 一句一个中心 | 每句只表达一个主要事实、主张或动作。 |
| G3 | 先条件，后动作 | 读者在执行前先知道前提、风险和限制。 |
| G4 | 明确责任关系 | 能确定时写清“谁对什么做什么”。不得臆造执行者。 |
| G5 | 保留语气 | “可能”不改成的确发生，“建议”不改成“必须”。 |
| G6 | 一致优先于变换 | 不为避免重复而轮换近义词或改写相同操作。 |
| G7 | 简短服从完整 | 先拆逻辑，再删赘词；不删必要成分。 |
| G8 | 结构外显 | 用编号、段落和连接词显示顺序、因果、条件与对比。 |

建议处理顺序：**事实与逻辑 → 歧义 → 术语 → 句式 → 长度 → 风格。**

## 3. 词汇与术语约束

### V1 一个概念使用一个名称

同一文档中，同一对象、动作和状态使用同一名称。不要交替使用“缓存、高速缓存、cache”，除非首次定义或语境确实不同。

新增或修改术语时，更新 `terms.md`。检查器不能可靠判断近义词是否同义。

### V2 使用直接动词

把名词化结构改成直接动作：

- “对日志进行分析” → “分析日志”。
- “完成配置文件的修改” → “修改配置文件”。
- “实现性能的优化” → “优化性能”。

保留有独立技术含义的名词，不机械删除所有“进行、实现、完成”。

### V3 删除无信息措辞

删除或具体化“相关、适当、某些、一定程度上、等等、必要时、视情况而定”等模糊表达。无法具体化时保留，并标记需要人工确认。

删除没有可验证依据的宣传词，如“强大、无缝、极致、革命性、完美、最佳”。“高效、智能、快速”等词只有在有判据或测量结果时保留。

### V4 统一要求强度

| 词语 | 固定用途 |
|---|---|
| 必须 | 强制要求。 |
| 不得 | 明确禁止。 |
| 建议 / 不建议 | 推荐，但允许例外。 |
| 可以 | 权限、选项或可行方式。 |
| 可能 | 不确定性或可能性。 |
| 预计 | 基于现有信息的预期，不表示保证。 |

避免用“应该”同时表示义务和预期。根据真实含义改成“必须、建议”或“预计”。

### V5 区分近义技术动作

- **检查**：查看内容或状态。
- **验证**：依据预期结果或判据判断是否满足要求。
- **确认**：核实一个指定事实或状态。
- **删除**：使数据或对象不再存在。
- **移除**：解除包含、连接或引用，不必然销毁对象。

项目定义优先。不得为了简短把 `verify`、`confirm`、`validate` 机械翻成同一个词。

### V6 首次解释陌生术语

读者可能不知道的项目术语，在首次出现时给出一句定义。后续使用同一个名称，不重复解释。

### V7 保持数字与单位可核对

保留数字精度、比较范围、单位和时间基准。统一同一文档的单位写法。不得把“约 10 ms”改成“10 ms”，也不得把“超过”改成“达到”。

## 4. 句式与段落约束

### S1 操作句使用祈使句，一步一个动作

连续动作使用编号列表。两个必须同时发生的动作可以共用一个句子。

不推荐：

> 打开文件并检查第三行，然后保存结果。

推荐：

> 1. 打开文件。
> 2. 检查第三行。
> 3. 保存结果。

### S2 把条件和例外放在动作前

- 不推荐：“缓存为空时重新构建索引”若后接多个例外，容易隐藏范围。
- 推荐：“如果缓存为空，重新构建索引。”

多个条件分别列出。不要在一个长句中堆叠“如果、除非、但是当、否则”。

### S3 描述句优先使用主动语态

执行者已知且与读者有关时，写“清理任务删除临时文件”，不写“临时文件被清理任务删除”。执行者未知或无关紧要时，可以保留被动句。

### S4 使用句长作为审查信号

| 文本 | 默认上限 | 性质 |
|---|---:|---|
| 中文操作句 | 40 个计数单位 | 本地建议，可配置 |
| 中文描述句 | 50 个计数单位 | 本地建议，可配置 |
| 英文操作句 | 20 词 | STE 可迁移规则 |
| 英文描述句 | 25 词 | STE 可迁移规则 |

中文计数单位 = 汉字数量 + 英文单词、数字和受保护代码跨度的数量。标点不计数。混合句只要包含汉字，就使用中文阈值。

超限先检查是否有多个事实、动作或逻辑关系。不要为满足字数删除条件、例外或语气。必要长句可以保留，但需说明理由。

### S5 拆开多层修饰和因果链

一个名词前有多个修饰语时，先确认修饰关系，再用短句或列表拆开。出现两个以上“的”时进行人工复核，不自动判错。

不推荐：

> 新的用于处理用户上传的实验数据的异步任务调度模块。

可改为：

> 新模块调度异步任务。这些任务处理用户上传的实验数据。

改写前必须确认“新的”修饰模块还是任务。

### S6 消除模糊指代

“这、那、它、其、该”必须指向唯一、明确的对象。不要用“这”指代前一整段。存在歧义时重复名词。

- 不推荐：“服务更新缓存，这可能导致延迟。”
- 推荐：“服务更新缓存。缓存更新可能导致延迟。”

### S7 保留必要句子成分

描述句省略主语后可能改变执行者时，补出主语。操作步骤使用祈使句，不必反复写“你”。

把否定词和“只、仅、所有、每个、不、未”放在其限定的对象附近。避免“并非不、不是没有”等双重否定。

### S8 明确连接关系

使用“因为、因此、如果、但是、然后”等词表达真实关系。不要只用“并”连接因果、并列和顺序。

避免“和/或、及/或、and/or”。根据含义写成“A 或 B”“A 和 B”“A、B 或两者”。

### S9 一段一个主题

每段通常不超过 6 句。复杂序列、三个以上并列项和多个例外使用垂直列表。列表项保持语法结构一致。

### S10 安全文本先于操作

本地约定：

- **警告**：可能导致人员受伤或死亡。
- **注意**：可能导致设备、数据或其他对象损坏。
- **说明**：提供补充信息，不隐藏必须执行的动作。

不得自行提高或降低风险等级，不得补充原文没有的防护步骤或安全保证。

## 5. 中英文使用边界

### B1 中文承担叙述

解释、推理、步骤、结果和总结默认使用中文。把常见概念写成中文，不写成无必要的中英混写。

- 不推荐：“在 config 里设置 cache 的过期时间。”
- 推荐：“在配置中设置缓存的过期时间。”

如果 `config` 是真实标识符，则必须保留：`在 config 中设置缓存的过期时间。`

### B2 保留不可替换的英文

以下内容保持原样：

- 代码、命令、参数、标识符、路径、URL 和错误原文。
- 产品名、协议名、标准名和界面标签。
- 无法在不损失精度的情况下翻译的引用或术语。

普通叙述中的英文词与代码标识符要区分。`cache` 作为代码名可以保留，作为普通名词通常写“缓存”。

### B3 允许必要的英文术语

满足以下任一条件时，可以使用英文术语：

- 没有稳定、通行的中文译名。
- 英文是目标读者实际使用的主要名称。
- 项目术语表明确保留英文。
- 使用中文会与代码、界面或外部资料失去对应关系。

把决定加入 `terms.md`，不要临时反复切换。

### B4 首次定义缩写

不常见缩写首次出现时，使用“中文名称（缩写）”。英文全称有助于理解或检索时，使用“中文名称（英文全称，缩写）”。后续只使用一种形式。

示例：“应用编程接口（API）”。目标读者已经熟悉且术语表已登记的缩写可以直接使用。

### B5 不默认生成双语对照

一个文档或段落只设一种主要叙述语言。只有读者、交付格式或用户明确要求时，才生成双语版本。双语版本保持术语、条件、数字和语气一一对应，不逐句重复相同内容来填充篇幅。

### B6 英文成段时使用英文规范

英文技术段落应用 STE 风格的主动语态、简单时态、单句单动作和 20／25 词上限。需要官方合规时，必须另查合法取得的官方标准与词典。

### B7 保持排版一致

中文句子使用中文标点，完整英文句子使用英文标点。中英文之间是否加空格、数字与单位之间是否加空格，按项目既有约定统一；同一文档不要来回切换。

## 6. 常见错误检查清单

### 6.1 含义保真：发现即阻断交付

- [ ] 执行者、动作和对象没有被偷换。
- [ ] 条件、例外、否定、范围和比较关系完整。
- [ ] 数字、单位、时间和精度完整。
- [ ] “必须、不得、建议、可以、可能、预计”没有被互换。
- [ ] 没有新增原因、步骤、机制、风险、性能或结论。
- [ ] 代码、命令、路径、标识符、界面文本和引用保持原样。

### 6.2 结构与句式

- [ ] 每个操作步骤只有一个动作。
- [ ] 条件和警告位于相关动作之前。
- [ ] 描述句优先明确执行者；合理被动句没有被机械改写。
- [ ] 长句已按逻辑拆分，而不是只删词。
- [ ] 每段只有一个主题，通常不超过 6 句。
- [ ] 列表项结构一致，顺序步骤使用编号。
- [ ] 没有不必要的分号、双重否定和多层名词修饰。

### 6.3 词汇与指代

- [ ] 同一概念只用一个名称。
- [ ] “检查、验证、确认、删除、移除”等词按定义使用。
- [ ] “这、它、其、该”都有唯一明确的先行对象。
- [ ] 无信息措辞和宣传词已删除或具体化。
- [ ] 陌生术语和缩写已在首次出现时解释。

### 6.4 中英文边界

- [ ] 普通叙述使用中文，没有无必要的 `cache`、`config` 等混写。
- [ ] 必要英文有明确理由，并与术语表一致。
- [ ] 标识符和普通名词没有被混为一谈。
- [ ] 没有默认生成冗余的逐句双语对照。
- [ ] 英文成段时另按英文规则检查。

### 6.5 机械检查后的必要人工复核

- [ ] 检查器发现已逐条确认，误报已忽略并记录原因。
- [ ] 检查器没有覆盖的术语、语义保真和修饰关系已人工检查。
- [ ] 未把“零发现”写成“官方合规”或“通过认证”。

## 7. 简短示例

### 示例 1：连续操作

**原文**

> 缓存为空时重新构建索引并检查日志，失败的话重启服务。

**改写**

> 如果缓存为空，执行以下步骤：
>
> 1. 重新构建索引。
> 2. 检查日志。
> 3. 如果构建失败，重启服务。

依据：S1、S2。保留重试条件和动作顺序。

### 示例 2：名词化与宣传词

**原文**

> 利用强大的缓存机制对查询性能进行优化。

**改写**

> 使用缓存优化查询性能。

依据：V2、V3。删除无测量依据的“强大”，直接使用动词。

### 示例 3：模糊指代

**原文**

> 服务启动后更新缓存，这可能导致延迟。

**改写**

> 服务启动后更新缓存。缓存更新可能导致延迟。

依据：S6。保留“可能”，并明确延迟的来源。

### 示例 4：中英文边界

**原文**

> 在 config 里设置 cache 的 TTL。

**普通配置叙述**

> 在配置中设置缓存的生存时间（TTL）。

**`config` 是真实标识符时**

> 在 `config` 中设置缓存的生存时间（TTL）。

依据：B1、B2、B4。是否保留英文取决于它所指的内容，而不是机械替换。

### 示例 5：保留不确定性

**原文**

> 请求可能已超时，因此结果可能不完整。

**改写**

> 请求可能已超时。结果可能不完整。

不得改成“请求超时，结果不完整”。依据：G5、S4。

### 示例 6：必要英文

**中文原文**

> 如果缓存为空，重新构建索引。

**必要英译**

> If the cache is empty, rebuild the index.

依据：B6、S2。英文仍须另查官方词典，才能声称词典合规。

### 示例 7：安全提示

**原文**

> 删除数据前先备份，否则数据可能丢失。

**改写**

> 注意：删除操作可能导致数据丢失。
>
> 1. 备份数据。
> 2. 删除数据。

依据：S10。风险等级和可能性保持不变。

## 8. 迭代方法

1. 记录真实改写中反复出现的问题。
2. 把问题写成可观察、可判定的规则，避免只写“更自然、更高级”。
3. 为规则添加一个正例和一个反例。
4. 把稳定的术语决定写入 `terms.md`，附使用条件。
5. 调整中文句长阈值或新增自动检查后，用真实文本验证误报。
6. 保留规则编号，避免已有审查记录失去参照。
